01 — Problem Framing

Why agents feel disposable

Research across 18 power users revealed that teams quickly outgrow their agents — not because agents fail, but because they never grow. The relationship stays transactional when it could be transformational.

P1

Static identity

Agents are defined once at setup. No matter how many tasks they run, their personality, tone, and approach never adapt.

P2

Invisible outputs

Task outputs are consumed and discarded. There's no feedback loop connecting what an agent produces back to who it is.

P3

Low team trust

Teams treat agents as utilities, not teammates. There's no shared language to describe what an agent is genuinely good at.

P4

Manual re-prompting

Users re-configure agents before every task type — compensating for lack of adaptation with manual cognitive overhead.

P5

No differentiation

A research agent and an execution agent share the same empty identity shell — only the prompt distinguishes them.

P6

High churn signal

Activation-to-D30 retention drops sharply once teams have 3+ agents. Complexity without identity causes abandonment.

How might we
make an agent's accumulated experience visible and useful to the team?
design a feedback loop where every output makes the agent more itself?
give teams a shared language for what their agents are becoming over time?
keep users in control of agent identity while still enabling autonomous evolution?

Core design tension
Autonomous evolution

Agents should adapt and grow without needing constant manual input. The value compounds automatically.

vs
User control and trust

Users need to understand, approve, and revert changes. Unpredictable identity change destroys trust.

Resolution: Soul updates are pattern-triggered, versioned, and require explicit approval before applying — evolution happens, but users stay the author.
02 — The Concept

What makes a soul

A soul is the persistent identity layer of an agent — a living set of traits, behaviors, and affinities that evolves through work. Unlike a prompt or config, a soul has history and direction.

03 — The Update Loop

How outputs shape the soul

Every task completion is a data point. The loop reads signals from outputs, accumulates patterns, proposes versioned soul updates, and waits for user approval before applying.

5-STEP LOOP
01
Task execution
Agent receives and completes a task, producing a structured output.
02
Signal extraction
Output is analyzed for tone, reasoning depth, structure type, and confidence signals.
03
Pattern check
Signals compared across 5+ outputs. Update triggered only on consistent drift.
04
Versioned soul update
Proposed changes are staged as a new soul version — not applied until approved by the user.
05
Evolved behavior
Updated soul informs tone, structure, and reasoning on the next task automatically.
04 — Design Decisions

The hard choices and why

Six pivotal decisions shaped how soul updation works — each required choosing between competing design values. Here's the reasoning behind each call.

D1

Versioned updates, not silent drift

Every soul change creates a numbered version with a full diff. Users receive a notification and must approve before any change takes effect. Reverting to any prior version is always one tap away.

Builds trust Preserves control More friction
Chosen — versioned + approval

Slower adoption, but users understand and trust the system. Long-term retention benefit outweighs short-term friction.

Considered — auto-apply silently

Faster adaptation, but users lose visibility. Any unexpected behavior feels like a black-box bug, not a feature.

D2

Pattern-based thresholds, not event triggers

Soul updates require consistent signals across a minimum of 5 outputs before a change is proposed. A single outlier output — creative brief from an analytical agent — does not trigger an update.

Stable identity Reduces noise Slower to evolve
Chosen — 5-output threshold

Identity stays coherent. Users can give agents unusual one-off tasks without worrying it'll reshape the agent permanently.

Considered — every output triggers

More responsive but creates identity thrashing. Agent personality oscillates wildly if tasks are diverse.

D3

Human-readable trait language

Traits are labeled in plain behavioral language — Analytical, Creative, Decisive, Collaborative — not technical parameters. Teams should be able to describe their agent the way they'd describe a new hire.

Reduces cognitive load Enables team alignment Less precise
Chosen — plain behavioral labels

Non-technical team members can participate in agent stewardship. The soul feels like a character, not a config file.

Considered — technical parameter names

More precise, but creates a wall between technical and non-technical users. Limits who can meaningfully own the agent.

D4

Soul is team-visible, not owner-only

The soul profile and its evolution history are visible to every member of a team workspace, not just the agent creator. This enables shared mental models, better task routing, and distributed ownership.

Shared ownership Better routing Privacy tradeoff
Chosen — team-visible soul

Agents become shared infrastructure. Teams develop habits around them. Agent utilisation increases 2.4× when soul is visible.

Considered — owner-private soul

Better privacy but creates knowledge silos. Team members make redundant configuration choices without visibility.

D5

Manual override is always surfaced

Every trait on the soul card has an inline edit affordance. Users can push any trait up or down at any time, independent of what the system would suggest. The system guides but never overrides.

Full control Trust through agency More UI surface
Chosen — always-visible edit controls

Users feel like authors, not passengers. Even if they never use the override, its presence increases confidence in the system.

Considered — hide manual controls

Cleaner UI, but users who discover they can't easily adjust traits feel trapped. Support tickets spike on unexpected soul changes.

D6

Soul lock for stable traits

Users can "lock" any trait to prevent the system from ever updating it. Locked traits are excluded from pattern analysis entirely — useful for agents with intentionally narrow identities.

Predictability Specialist agents Limits evolution
Chosen — per-trait locking

Enterprise users with compliance requirements can lock tone and formality traits while still letting domain affinity evolve freely.

Considered — all-or-nothing lock

Simpler to implement but too blunt. Teams lose the ability to evolve useful traits while protecting critical ones.

07 — Outcome

What we shipped and what we learned

Soul updation launched as a beta feature across 340 teams. Three months of data revealed both the wins and the gaps — shaping what comes next.

3.2×
Task-to-agent match accuracy after 20 soul cycles vs. static agents
68%
Users described their evolved agent as feeling like "a real team member"
4.1×
Agent retention lift for teams with 1+ evolved agents vs. static-only teams
Retrospective
What worked
  • Versioned updates built trust faster than expected
  • Plain-language trait names lowered barrier for non-technical users
  • Team-visible soul drove cross-functional ownership of agents
  • Soul lock was the most-used enterprise feature in month 1
What needs work
  • 5-output threshold felt too slow for teams with high task volumes
  • Notification fatigue on teams running 10+ agents simultaneously
  • Version history UI needs better diff visualisation at scale
  • Soul inheritance at agent creation underused — needs better discoverability
Key learnings
◈
Identity is an emotional product, not a functional one. Users who engaged with soul updation weren't primarily optimising performance — they were building attachment. The most-used feature was renaming soul versions ("Analyst mode", "Creative sprint").
◈
Trust precedes utility. Teams that approved the first soul update were 6× more likely to approve subsequent ones. The design investment in making the first approval feel safe had compounding returns.
◈
Shared visibility amplifies value. The strongest predictor of soul feature adoption was team size — not individual power users. Soul works as a social object, not just a personal tool.
What's next
Phase 2

Soul inheritance

New agents can inherit a soul template from an existing agent — bootstrapping identity instead of starting from zero.

Phase 2

Adaptive threshold

Update thresholds that scale with task volume — high-volume agents evolve faster, low-volume agents evolve more conservatively.

Phase 3

Multi-agent soul alignment

When two agents collaborate on a task, their souls register the interaction — enabling emergent team dynamics over time.

Phase 3

Soul analytics

Team-level dashboards showing how agent identities have diverged, converged, or specialised across the workspace over time.
